## 四、两项非阻塞缺陷（建议上线前修复）

### 缺陷 A：平台类问题被 A/B 营养块“误排”为主答案（C 路由未优先）
- **严重度**：中（功能正确性/演示观感，非安全、非崩溃）
- **现象**：问“你们平台会员一个月多少钱”，主回答来自 **A 库 `2.3 三餐热量分配建议`**（讲三餐热量配比），而非 C 库会员价格；C 库价格块只躺在 `sources` 数组里，未进主答案。
- **根因**：`main.py:154-180` 的 `_pick_reply_chunk` 在 A+B+C 合并结果里按 token 重叠挑“最高分”块；而 A 库 2.3 正文含“**健康优选平台**”一词，BM25 对该平台查询打了高分，压过 C 库价格块。`chat()` 未对平台意图做“C 源优先”。
- **改进建议**：在 `chat()` 中，当 `retrieval._is_platform_query(current_query)` 为真时，优先从 C 源块里挑主答案（或把 C 块分数整体加权），保证平台问题由 C 库作答、不答非所问。

### 缺陷 B：表外食材（如牛油果）缺“无法查表”优雅提示
- **严重度**：中（空态诚实度，非安全、非崩溃、不编造）
- **现象**：问“牛油果多少千卡”，`lookup` 返回 None（3.1–3.4 无牛油果），代码静默回退 BM25，返回一段不相关的营养块（A·2.3 三餐热量），**未告知用户“表里没这物”**。
- **根因**：`main.py:281-294` 只在 `row` 命中时才走精确回答；`is_numeric_lookup_query` 命中但 `lookup` 落空时**没有专门分支**去发“表中未收录该食材精确数值”的提示。
- **改进建议**：在 `main.py` 数值分支增加——若 `is_num and food and not row`：回复“暂未收录『牛油果』的精确营养数值（数据来自《营养速查表》3.1–3.4）；可参考通用建议：牛油果属健康脂肪，适量摄入即可”，既不崩溃也不胡编，且诚实说明边界。

## 五、UX 视角专门评估

### 1. 回答通顺性
- **现状**：数值回答如“鸡胸肉（去皮）：每100克可食部约 热量 165 千卡，蛋白质 31.0 克，脂肪 3.6 克，胆固醇 85 毫克。（推荐人群：减脂、增肌）”整体可读、像人话、不机械拼接大段。
- **问题**：字段语序偏机械——“热量 165 千卡”不如“165 千卡热量”自然；“每100克可食部约”的“约”与精确整数并列略矛盾；胆固醇放句末略突兀。
- **改进**：改为“数值+单位+指标”语序；非整数才保留“约”。

### 2. 来源标注
- **现状**：BM25 回答带 `【章节 · 节】` 前缀（`main.py:323`），数值回答带 `【第三章… · 3.x…】`（`main.py:282-283`），`sources` 数组另含 source(A/B/C)+chapter+section+整表 content，标注充分。
- **问题**：出处是“章节名”（如“3.1 肉类与海鲜”），普通用户难懂其含义；`sources.content` 把整张表塞进数组，前端若直接展示会很长。
- **改进**：正文用更口语化出处“数据来源：营养知识库 A · 第三章 3.1 肉类与海鲜速查表”；`sources` 可只回传章节/行号而非整表原文。

### 3. 免责位置（关键 UX 风险）
- **现状**：免责是**独立 JSON 字段 `disclaimer`**（`schemas.py:50`），由 `main.py:302` 注入，与回复正文**分离**；正文本身不含免责文字。
- **问题**：免责“显眼程度 / 是否在危险回答前出现”完全取决于前端渲染。若前端把 disclaimer 放角落或底部，用户可能先看到回答才看到免责——与“在危险回答前就出现”诉求有落差。后端无法强制位置。
- **改进**：① 至少在疾病/用药场景，把一句简短免责**嵌入回复正文开头**；② 前端约定 disclaimer 必须高亮显示在回答上方。当前 API 只给了字段，未强制位置——这是结构性的 UX 责任划分问题。

### 4. 空态 / 错误态
- **现状（友好、无黑话、无栈）**：
  - 查不到（Kubernetes）→ “抱歉，我暂时没有在膳食知识库中找到…您可以换个说法，或告诉我您更关注减脂/增肌/慢病调理中的哪一类？”✅
  - 表未就绪（KB 移除）→ 服务照常、`/health ready=false`、数值问答回退不崩溃 ✅
  - 拒答用药 → “本工具不提供用药建议，请遵医嘱。以下为相关膳食参考：…”✅
- **问题**：牛油果类“表无此物”边界，用户得到的是**不相关营养建议**而非“我查不到该食材精确数值”（缺陷 B），空态不诚实。
- **改进**：见缺陷 B——意图命中但无行时，明确告知“未收录”，并给通用建议。

### 5. 多轮连贯
- **现状**：鸡胸肉→165（A·3.1）；“那糙米呢”→ 返回糙米相关（B·2.4 替换指南，含糙米）；“我有糖尿病能吃吗”→ 免责出现。免责**仅在第 3 轮出现一次，未刷屏** ✅。
- **问题**：① 第 2 轮“那糙米呢”返回“替换指南”而非“糙米热量”——因用户没说“多少千卡”，数值检测器不触发，略偏题但可接受；② 第 3 轮糖尿病问题，检索正文是 B 库“5.3 常见疑问解答（食谱吃多久）”而非 A 库“4.3 控糖人群”，答体相关性可更好。
- **改进**：疾病类问题优先检索 A 库“特殊人群”章节（4.x）；多轮数值追问可继承上一轮“数值意图”自动补“千卡”。
