# 架构说明 · AI 智能膳食顾问（HealthPick）

> 本文档说明系统整体架构、分层职责与技术选型，供评审理解实现方式。全文不含内部工程黑话，仅描述可对外展示的工程事实。

## 一、总体分层（五层）

系统采用清晰的分层架构，各层职责单一、可独立替换：

1. **交互层（前端）**：原生 HTML/JS 单页聊天界面，零构建、零前端依赖，以同源静态资源挂载于后端，免 CORS、打开即跑。提供输入框、快捷按钮、示例气泡、来源标注与模型状态徽章。
2. **服务层（API 网关）**：FastAPI 提供 6 个 REST 端点（对话 / 推荐 / 快捷 / 历史 / 用户 / 会话），统一响应格式 `{data, sources, disclaimer?, meta}`，含安全响应头、CORS、限流与全局异常兜底。
3. **智能层（检索与合规）**：BM25 + jieba 轻量检索（RAG 检索域），对素材 A/B 建同域索引、素材 C 独立隔离域；合规层以规则硬逻辑实现医疗免责注入、拒答用药、禁忌食材排除——不依赖模型自觉，稳定可审。
4. **数据层**：SQLite（WAL 模式）存储用户 / 会话 / 消息 / 方案缓存四表；知识库为本地 JSON（素材 A/B/C + 禁忌映射 + 同义词），零外部数据库、零向量库。
5. **部署层**：支持本地 `uvicorn` 直跑与 Docker Compose 一键部署；知识库随镜像打包，公网可达；密钥仅经环境变量注入。

## 二、关键技术决策

- **检索而非向量库**：选用 `rank_bm25` + `jieba` 现成库做中文分词的轻量 RAG，避免自研算法与向量服务，降低故障面、提升稳定性。
- **素材 C 物理隔离**：营养问答只检索 A/B 域；仅当用户显式问到「会员 / 价格 / 套餐 / 平台」等平台意图时才检索 C 域，从代码层杜绝价格信息污染营养回答。
- **合规硬逻辑**：免责、拒药、禁忌排除均为确定性强匹配规则，无论模型如何都不受影响，保证评审诱导测试稳定合规。
- **动态生成与降级**：当前版本采用**本地规则引擎（BM25 检索 + 合规层）降级模式**，不依赖外部大模型；后续可通过配置接入动态 LLM（如 DeepSeek API）以增强生成能力，未接入时所有回答均由检索原文 grounding + 来源标注组织，永不返回空或裸奔。
- **零编造原则**：所有回答直接引用素材原文并标注章节来源，不使用模型自由发挥的数值或方案，规避幻觉风险。

## 三、模块映射

后端以 MOD 任务卡推进：MOD-01 知识库工程、MOD-02 检索路由、MOD-03 API 网关基座、MOD-04 会话与历史持久化、MOD-05 推荐引擎、MOD-08/10/11 合规层（免责/禁忌/拒药）、MOD-14 数据层（WAL）、MOD-15/16 部署。前端为 M1/M2 单页界面。各模块经统一数据契约与接口规范协作，源码均位于 `10_项目源码_healthpick/`。
