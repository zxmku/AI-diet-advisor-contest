# 系统架构说明 · AI 智能膳食顾问（HealthPick）
> **版本：v1.20（最终交付版）**

> 本文档按赛题"系统架构说明"要求撰写，覆盖：前后端/平台架构、知识库挂载方式、推荐逻辑设计、多轮对话实现、异常处理策略、平台选择理由、核心工作流节点、Prompt 设计思路。全文用工程事实说话，不含内部迭代黑话，便于评审直接理解。

## 一、前后端与平台整体架构

系统采用**前后端一体、纯本地运行**的架构，分五层：

1. **交互层（前端）**：单文件移动端聊天界面（原生 HTML/JS，零构建、零前端框架），由后端同源静态挂载，免 CORS、打开即用。提供输入框、快捷按钮、示例气泡、来源标注、模型状态徽章、历史会话面板、首屏场景卡、一餐卡（含采购清单）、朗读按钮、成长记忆状态条、用户档案抽屉等。
2. **服务层（API 网关）**：Python + FastAPI 提供统一 REST 接口，所有响应遵循同一契约 `{data, sources, disclaimer?, meta}`（`meta.model` 标识当前模型、`meta.degraded` 标识是否降级）。
3. **智能层（检索 + 合成 + 确定性工具 + 合规 + 适配器）**：BM25 + jieba 轻量检索（RAG 域）；可选 LLM 在检索结果之上合成自然语言；确定性一餐生成器、饮食台账、情感陪伴、用户档案聚合、若干管道适配器（时段感知 / 语音 / 健康状态 / 点单决策 / 成长记忆注入 / 推荐解释）；合规层以规则硬逻辑实现免责、拒药、禁忌排除、输入校验；成本闸门在真实模型调用前做预算/缓存/限速/记账四重保护。
4. **数据层**：SQLite（WAL 模式）存储用户 / 会话 / 消息 / 方案缓存 / 饮食台账；知识库为本地 JSON，零外部数据库、零向量库。
5. **部署层**：双轨——本地一键脚本（Windows .bat，端口 8137）与 Docker Compose 容器（8137:8000，命名卷持久化）；知识库与前端随镜像打包；密钥仅经环境变量注入。

## 二、知识库挂载方式

知识库是三份本地 JSON 素材（A 营养基础 / B 个性化方案 / C 平台服务），挂在后端 `knowledge/` 目录下，以**物理隔离 + 按需检索**的方式组织：

- **A+B 同域**：营养基础与方案合并建一个 BM25 索引，作为营养/方案核心检索域。
- **C 独立隔离域**：平台价格/会员/企业方案单独索引，**仅当用户问题命中平台意图词表（会员/价格/收费/企业/SaaS/API/套餐/订阅/开通/升级/专业版/联系我们等）时才检索**，从代码层杜绝平台商业信息污染营养回答。该意图词表是单一事实源，检索层与对话层共用，避免词表漂移导致平台问法漏检。
- **纯本地检索**：只用 `rank_bm25` + `jieba`，不调用任何向量库或 embedding 服务。
- **同义词扩展**：`synonyms.json` 把口语/别名归一为标准词（如 鸡脯肉→鸡胸肉、西红柿→番茄、减重→减脂），提升对标准表述知识块的命中。
- **零改写**：检索只回"原文块 + 来源（文档名 + 章节标题）"，回答由上层（本地规则或 LLM）基于这些块生成，保证数值与结论可溯源、不编造。

## 三、推荐逻辑设计

所有推荐都**基于素材真实内容、不引入素材外数值**：

- **确定性一餐生成**：当用户表达"做顿饭/今晚吃什么"等意图时，按目标人群（消息目标词 → 会话画像 → 追问目标）从素材 B 取食材，构成"主蛋白 + 主食碳水 + 蔬菜 + 好脂肪"四槽位；每个食材的热量/蛋白/碳水/脂肪一律查营养速查表真实值 × 份量计算，表外食材标注"约计"不编造；禁忌食材在槽位与同族替换中全链路剔除；做法取自素材 B 与速查表"推荐做法"列并带来源；采购清单由一餐食材派生。
- **推荐解释**：在素材 B 方案字段（热量区间 / 食材组合）基础上生成"为什么适合你"的结构化说明，不引入素材外数值。
- **点单决策工具**：覆盖 7 类场景 × 3 类目标（减脂/增肌/慢病），只做定性建议、不引用素材外数值。
- **前端渲染**：检测到一餐结构即渲染一餐卡，检测到决策结构即渲染点单建议，未命中保持原契约。

## 四、多轮对话实现方式

- **持久化**：会话与消息落库（SQLite），历史真实可读，跨轮上下文可回溯。
- **跨轮记忆**：用户声明的过敏/禁忌与目标人群持久化进会话，后续轮次自动生效（"记得我"）；首次声明过敏以顾问口吻追问一次细分类型。
- **否定式处理**：疾病判定前剥离"没有/没得/正常/不是"等否定结构，用户否认患病时不误贴疾病画像、不误加控糖引导。
- **归属校验**：会话画像（目标/禁忌）读写均校验 `user_id` 归属，杜绝跨用户串号与档案泄露。
- **只读用户陈述**：会话历史扫描疾病延续/画像引导时只统计用户消息，模型或检索输出不当作事实。

## 五、异常处理策略（降级不崩）

全链路以"确定性兜底"替代"报错中断"：

- LLM 不可用、网络超时、依赖缺失 → 无缝降级本地规则（检索原文直出 + 来源）；
- 知识库缺失 / BM25 构建失败 → 退化为规则分支；
- 数据库异常 → 非致命，不影响当次返回；
- 成本闸门故障 → 按放行处理，不因闸门误伤主流程；
- 语音（TTS）缺失或失败 → 返回 503，前端 toast 提示，不打断对话；
- 任何失败路径都有明确兜底文案，绝不"裸奔"。

## 六、平台与技术选型理由

- **纯本地、零外部服务**：Python + FastAPI + SQLite + 纯 BM25，前端零依赖、零构建。整套系统可在无网环境跑通，演示与提交都不依赖第三方在线服务，稳定性与可复现性强。
- **体现真实工程能力（非白标）**：合规护栏、数值引擎、知识隔离闸门、成本闸门均为手写的确定性逻辑，而非套用现成对话平台模板；赛题要求的"不编造、不混库、真实来源、禁硬编码回复"都由这些自研模块落地，可逐条审计。

## 七、核心工作流节点

一次对话请求的派发顺序（意图优先级，防劫持）：

> **用药硬拦截 → 数值精确问答 → 一餐生成 → 点单决策 → 检索/LLM 合成 → 闲聊（非膳食）**

- **用药硬拦截**：命中用药词（含通用名与命名族尾缀，且对"山药/药膳"等白名单豁免）先拒答并带免责，不进入任何推荐分支。
- **数值精确问答**：含食材 + 营养问法（如"鸡胸肉多少千卡"）直接查速查表返回精确值，不被一餐/点单劫持。
- **膳食 vs 闲聊门控**：以"营养概念 + 目标方案 + 健康疾病 + 食材名"判定膳食需求走 RAG，非膳食（打招呼/问身份/动物习性等）走自然闲聊，避免低相关检索污染回答。
- **合规层全程守卫**：免责、拒药、禁忌排除均为确定性规则，不依赖模型自觉，评审诱导测试稳定合规。
- **成本闸门**：真实模型调用前先做预算/缓存/限速/记账四重保护，接真模型也不会无上限消耗。

## 八、Prompt 设计思路

- **启用条件**：仅当配置 `DEEPSEEK_API_KEY` 时启用 LLM；否则系统整体走 local-rules（检索原文直出 + 来源标注），保证零配置也能运行、且同样不编造。
- **系统提示核心纪律**：
  1. 数值 100% 逐字引用素材，严禁推理编造；未收录则诚实说明"资料暂未收录"；
  2. 绝对不提供用药建议、不诊断疾病（此类问题已被上游合规层拦截，不进入生成）；
  3. 严守用户已声明禁忌，回答中不推荐任何禁忌食材；
  4. 平台商业信息仅依据素材 C，不在纯营养搭配中强推付费；
  5. 口语化、先共情后建议、表达精炼（约 200 字内）。
- **检索 grounding**：检索块以"来源 + 章节"标注后拼入上下文，模型严格基于这些块作答。
- **成长记忆注入**：基于饮食台账计算的坚持天数 / 今日记录，注入到检索回答、闲聊、陪伴三处调用，让模型能"结合昨天与今天"回应。
- **安全降级**：LLM 任何异常（网络/超时/非 200/解析失败/依赖缺失）一律返回空，由上层无缝降级 local-rules，绝不裸奔。
